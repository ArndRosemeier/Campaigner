# 05 — UI Specification

Tailwind + shadcn/ui, dark mode default (GM-at-the-table friendly), light mode
toggle in the top bar. Routing via react-router.

Top bar: app name, campaign switcher, Rules / Settings navigation, the
last-module shortcut (arrow + the name of the module whose reader was opened
last, one click back to it — hidden until a reader has been opened), New
Module on campaign routes, Ctrl+K quick-find, generation language, help and
theme. Directly below it, the **campaign bar** renders the campaign-level tabs —
Modules / Workspace / Deliverables / Graph, Modules first (the central view
the rest feeds) — on every route, disabled (with an
"Open a campaign first" hint) while no campaign is open. On nested screens the
bar's right side shows a breadcrumb (Campaigns / Modules / *module title* / Battle
table), so deep screens always state where they are and exit in one click.
The retired `/play` route and `▶ Play` button do not exist.

### Quick-find (Ctrl+K)

The palette follows the workspace scope preference. Artifact hits search
name/tags/summary/aliases; global hits are labeled **Library**. Module/part and rule
hits share the palette. Enter navigates to an artifact or module; rule hits
open an inline preview with **Pin to Assistant**. With an empty query the
palette lists a **Go to** group — the campaign sections (Workspace, Modules,
Deliverables, Graph), Rules and Settings, and **Battle table (this module)**
on a module reader screen — so Ctrl+K doubles as an app map.

## Why a control cannot act (THE one way)

A control that cannot act must say WHY, in a way the user can actually
perceive — one device, shared by every surface:
`components/blocked-control.BlockedControl` (seam row in docs/18 §2.3, gotcha
in docs/18 §4). It is never a `title` on the control, and never a second
tooltip idiom.

- **Hover.** The wrapper is the Tooltip primitive's trigger, so the REASON has
  somewhere to land. The control inside cannot receive it: a natively
  `disabled` form control fires no pointer events at all in Chrome, and every
  shadcn Button adds `disabled:pointer-events-none` on top, so it is not even
  hit-tested — which is exactly why a `title` there never renders.
- **Keyboard.** While blocked the wrapper carries the tab stop (`tabIndex=0`)
  and the tooltip opens on focus. A `disabled` control cannot be focused, so
  without this half the reason is unreachable without a mouse.
- **Assistive tech.** The same sentence is rendered once into a visually hidden
  node that the wrapper points at with `aria-describedby`, so it is announced
  whether or not a popup is open.
- **Layout.** The wrapper is an `inline-flex` span in the control's place (pass
  its layout classes, e.g. `shrink-0`, through the wrapper's `className`).

Pass `reason: null` whenever the control CAN act: the wrapper is then an inert
span — same DOM shape, so a state flip never remounts or re-focuses the
control, and nothing is attached to it. A `title` mirror may stay beside a
reason (Firefox renders it) but it is never the device and never the only
statement.

**Not every blocked control needs one.** A control whose own label states the
state ("Saving…", "Creating…", "Regenerating…", "Reported"), a required input
left empty (a chat send with no text), and a list with nothing in it to act on
(the Versions menu's clear-all beside its own "No saved versions yet"
paragraph) are SELF-EVIDENT: disabled with no wrapper is correct for those, and
the pin says so explicitly. Everything else states a reason, and every reason
must be TRUE for the state that produces it and name the way out where one
exists ("wait for it (or press Stop)", "select the text to refine first").

## Progress dock

The app-wide dock reports every slow task (batch generation, module parts,
PDF builds). Its header hosts **Stop all**, which sweeps every running
generation: all four job queues (mob portraits, entity images, encounter
maps, module/campaign covers), every in-flight run, the module forge, a
running Writers'-Room chain, and a live canvas AI turn (chat / refine) — and
then SEALS the "no new units" gate, so a stopped orchestration does not start
its next kind, its next target, or its enqueue tail (lib/stopEpoch). The
whole thing is non-destructive: stopped runs stay resumable, cancelled rows
keep their Retry, a stopped job settles silently, and a cancelled run is
never reported as a failure. NOT covered (not generations, or no cancel
seam): PDF builds and backup jobs, and the queues' FAILED retry lists. Jobs that live somewhere (a persona run, a module mid-forge)
render their label as an **Open** button that navigates to the job — a run
opens preselected in the workspace persona panel (`?run=`), a module opens in
its reader. A module that is being forged also shows the live step ("Writing
part 2 of 5: …") on its Modules list row.

## Screen: Module reader (`/c/:campaignId/m/:moduleId`) — M6

The module reader is the only play view: table of contents/search on the left,
adventure prose and wiki-link chips in the center, entity panel on the right.
**A generated scene arrives as a SCENE BLOCK** (08-MODULE-DESIGNER §M4-B-2): a
`##`/`###` heading carrying the scene's `[[link]]` and its ENCOUNTER/EVENT tag,
then bold field labels (Where, First impression, Who is here and what they want
right now, The situation, What changed, If the party acts, Secrets, Leads,
Outcome) with the arrow bullets under "If the party acts". The reader has NO
scene-aware code and needs none: the block is ordinary markdown, so it renders
through the SAME `WikiMarkdown` as everything else — the heading as a heading,
the field labels as text, the bullets as a list, and the in-block `[[links]]` as
the ordinary resolved/unresolved chips. Parts written before the format (plain
prose: no heading, no labels) render exactly as they always did — nothing fails,
nothing migrates, and they stay hand-editable. What the reader does NOT show:
the ENCOUNTER/EVENT tag is a text convention, not a UI state — the reader
derives nothing from it, and whether a scene gets a battle map or a monster
roster is decided by its entity's recorded kind, never by the tag on the page.
Its shared Library / Campaign / Module scope control defaults to all scopes.
The entity panel's third list — **"Orphaned (unmentioned)"** (08-MODULE-DESIGNER
§M4-C) — tags module-owned rows this module's prose never mentions (amber
kind badge + "no mentions" per row) with a guarded per-row trash and a
count-gated destructive "Delete N orphans" toolbar button behind a confirm
dialog; the sweep keeps rows another module's prose, a battle, an encounter
roster, or a deliverable outline still uses, naming them in one loud result
toast (00-OVERVIEW "Orphaned (unmentioned)" vs the tree's module-less
Orphaned group). **A kept row is never offered**: it stays in the group as
**in use — <the sweep's own reason>** (e.g. `in use — roster entry "Risen
Lumberjack" of the encounter "Bog Ambush"`), with no trash button, and the
toolbar count, the confirm title and the confirm list only ever name rows a
sweep will actually delete (at zero the destructive control is absent — a
control that could only refuse is not an offer). The confirm copy says the
sweep re-checks every reference and names whatever it still finds in use.
The batch toolbar's buttons exist **per recorded kind** — a wiki-link name the
last name-normalization pass never saw (a chat turn, a hand edit, a board
rewrite, a restore) has no recorded type and therefore no button. The panel
reads the module text fresh on every display and, when it finds such names,
shows them in one line — "**N unresolved names have no recorded type yet —
classify them to get their batch buttons**" — beside a single
**Classify N new names** button (disabled while the module is generating;
while the name-normalization gate is closed the failure banner and its Retry
stand there instead). One click runs the same normalization pass as at
creation for those names only, toasts what it classified ("No new entity
names to classify" when a repeat click finds nothing), and the kind's
"Generate N <kind>" button reappears with the new count. A failure is loud:
the error is recorded on the module with the batch gate closed, and text the
user hand-edited is only rewritten after the review banner's consent (a
chat-applied part counts as hand-edited). The panel never classifies on its
own — displaying a module can never spend a model call.

A row counts as **detailed** when the name has an authored entity of its OWN —
not merely when *something* answers the wiki-link (docs/17 row 82). A bestiary
**creature row** (an `npc` carrying the rulebook chunk marker: ONE shared row per
cited creature, its portrait cached globally) is a real artifact the link
resolves to, but it carries no authored detail, so a name whose only row is one
is NOT detailed: it sits in the batch queue with its kind badge, and its row
carries a dashed **"bestiary only"** marker whose title (and screen-reader
sentence) names that shared row and the remedy — "generating it here creates
this module's own NPC of that name". Generating it lands a module-owned `npc`
that the module context then prefers, so the panel row, the entity card and the
reader chips all show the module's own entity from then on. A name the campaign
answers with an authored NPC (or the module with its own) is detailed and offers
nothing, and the marker never appears for it. The row still opens the stub
popover (per-entity generation), and in Images mode its checkbox is off with the
reason "Detail this entity first — images attach to its artifact": images attach
to an authored artifact, never to the shared creature row, whose portrait the
mob-portrait batch owns. The reader's chips are unchanged by this verdict — they
keep resolving a creature-backed name to the real row.

**"Generate everything"** (docs/17 row 80) is the sidebar's bulk fill: entity
details for **every** kind the module's text names, their images, encounter
battle maps and encounter mob portraits — every generation gap of this module,
the same work the canvas's "Resume automatic module creation" does, without that
control's precondition. It is **derived**, never stored: the button appears only
while the deviation against the FULL target (every entity kind in both lists,
maps and mob portraits on) is non-empty, and shows the work count on its face
("Generate everything (7)"). With nothing missing its place holds the passive
statement "**Nothing missing**" — never a permanently disabled button, which is
indistinguishable from a broken one. It is disabled with the honest reason
stated through the shared blocked-control device (§Why a control cannot act;
the `title` mirror stays beside it) while a generation is in flight (the module
generating, or this module's
queued/active image or map jobs), and for a module whose parts pass did not
finish it names the remedy instead: fix the **text** first ("Fix module
problems" on the canvas, or a hand edit) — a module whose parts never landed has
nothing to automate. While its OWN run is live the label reads "Generating…",
which is self-evident and carries no reason.

Confirming lists exactly what will be filled, in the same wording the canvas's
resume uses (one detector set, `deviationLines`), and the run is the SAME
pipeline: the incremental name-classification pass, then the name-normalization
pass when the batch gate is closed, then the post-generation sweep — additive,
so nothing that already exists is re-generated, re-detailed or overwritten. The
module's recorded `automationIntent` and its own automation fields are **never
written** (they stay the record of what creation was asked to automate). Legacy
modules — created before `automationIntent` existed, which the intent-bound
resume refuses — are served fully here. The run reports its outcome (one
completion toast naming what was generated and queued; a Stop all during it ends
it with an honest "stopped" toast).

**What it cannot fill, stated in the confirmation and here:** the module **text**
is never rewritten and no scene is created. Every gap it fills is an artifact
derived from text that already exists — a name the text wiki-links but that has
no artifact of its recorded kind, an entity with no image, an encounter without a
layout/map, an encounter whose roster still cites un-imaged mobs. A **fight the
prose stages without an `[[encounter]]` link of its own, or without an
`encounter` RECORD, is invisible to every derived detector in this repo** (the
encounter floor counts recorded canonical `[[encounter]]` links, the batches
read records): it is not a generation gap this control can see, and detecting it
would need a prose classifier over the spine and scene tags, which the owner's
own decision (docs/17 row 75: the tag stays prose) rejects. The remedy for that
case is the text path — "Fix module problems" on the canvas repairs a part that
falls short of the floor by rewriting its prose (with a durable snapshot).
**Battle table** opens the module's live board — offered both in the reader
header (a mode change, visible even with the contents sidebar collapsed) and
in the contents sidebar. Encounter rows offer **Run battle**. Module-owned
rows can be adopted back into the campaign. Recorded
encounter entities can be batch-detailed, and **Generate encounter maps** runs
a one-candidate unattended queue for module encounters still lacking layouts;
failures remain retryable and do not stop later jobs. The header mounts the
module cover hero (cover-generation arc: `ModuleCoverHero` — the banner
renders only when the module has cover art) with **Generate / Regenerate
cover** beside the other header actions; the modules list row mounts the
cover thumb (`ModuleCoverThumb`) with a compact icon-only generate
affordance. Both displays resolve through `useImageUrl(coverImageId)` — the
same artifact-cover path as the play cards — and render nothing while
loading/missing (no placeholder art). The reader and the list never render
in player-safe mode (the battle player-safe DOM contract mounts board
material only), and every other reader control is already an un-gated GM
control — so the Generate buttons join that set with no extra gate; covers
are shared art, never secrets (the player-audience PDF strips GM-only
material at render, covers round out the page as art).

### The chip's hover tooltip — the token the link was WRITTEN from

Owner request (docs/17 row 100), verbatim: *"i would like to have a hover
tooltip over all Wikilinks where the raw text of the link is displayed. Some
things are just not visible in the rendered version, like encounter
parameters."*

The rendered view shows the link's **display text** only: `[[Encounter:Ash
Gate|the gate]]` renders as a chip reading "the gate", and nothing on screen
says what it points at. So EVERY chip — resolved, unresolved and ambiguous —
carries a native `title` that **leads with the byte-exact source token** and
then keeps what the chip already said:

- resolved → `` [[ Ash Gate |the gate]] — NPC Ash Gate `` (the kind + name the
  tooltip always had);
- unresolved → `` [[Kael]] — Kael — not detailed yet `` (the old sentence
  survives INTACT as the tail — nothing the chip said before is traded away);
- ambiguous → `` [[Ash Gate]] — ⚠ 2 artifacts match “Ash Gate”: … `` (the old
  ⚠ candidate list survives as the tail).

**Byte-exact means byte-exact**: the token is shown as WRITTEN, including the
inner spacing the parser trims (`[[ Ash Gate |the gate]]` shows those spaces —
the name and display are trimmed for resolution and for the label, the token is
not). It is CARRIED, never reconstructed — a rebuild from name + display cannot
reproduce the spacing, and the pins are written so that a rebuild fails them
(docs/18 §4). The token is also on the element itself as `data-wiki-raw`, so
the carrier is inspectable independently of the tooltip string.

The mechanism is the **native `title`**, deliberately: the chip is a real,
non-disabled `<button>`, so its tooltip renders (the invisible-`title` defect
of docs/18 §4 applies to natively `disabled` controls only), and it adds NO
wrapper element inside flowing prose — the chips are `inline-flex` inside
module prose and a reader renders many of them, so wrapping each in a tooltip
trigger would risk layout drift at reader scale. `BlockedControl` is NOT used
here: nothing about a chip is blocked.

Surface coverage is automatic: every wiki-aware surface renders through the ONE
`WikiMarkdown` (module reader, canvas preview, peek modal, artifact-body
preview, part-text-editor preview, module board cards, the guide) and there is
no second chip renderer anywhere. The CodeMirror **editor** needs nothing — it
shows the raw text already, and its own wiki-decoration tooltip is untouched.
The **export path is elsewhere entirely** (`lib/modulePdf` / `lib/pdfExport`
never import `WikiMarkdown`, pinned structurally), and the carrier is minted at
React render time, so it cannot reach a PDF. The one exception row 100's arc
found — the single-artifact GM-notes/handout export printing `[[…]]` verbatim,
because `lib/markdown.markdownToText` was not wiki-aware — was RECORDED there
and pinned as the defect in `tests/lib/wiki-raw-export.test.ts`; **it is FIXED
(row 105)**: both single-artifact bodies now render through
`lib/markdown.markdownToDisplayText`, so an export prints the DISPLAY text
(docs/07 §Wiki-links in an exported document; docs/18 §2.3/§4), and that test
file asserts the fixed behaviour instead of recording the leak.

### Provenance captions — which model wrote this

Owner request (docs/17 row 93), verbatim: *"I would like you to put a very
small id below generated texts (in entity cards and the module), indicating
which model wrote this. And a small id below images indicating the image
model."* One presentation everywhere: the model id ITSELF, in the smallest
muted mono type (`text-[11px] text-muted-foreground/70`, selectable so it can
be copied), with no label words — a screen reader hears "Writing model: …" /
"Image model: …" through `aria-label`. One component renders it
(`components/writer-model-id.WriterModelId`), one rule decides it
(`domain/provenance.recordedWritingModel`: trim, `''`/null ⇒ NOT RECORDED).

Where it appears (APP ONLY — owner decision; it never reaches an exported PDF,
a deliverable or a model prompt):

- **Entity card (peek modal)** — `peek-writer-model` under the card's text
  (summary + body), and `peek-image-model` under the card's image banner.
  `NpcCard`/`EncounterCard` take an explicit `showWriterModel` opt-in that the
  peek modal sets; the battle table's GM-only "Open card" dialog does not, so
  no id appears on the table surface.
- **Module reader** — `premise-writer-model` under the premise, and
  `part-writer-model` under each part's prose (in player-safe mode too: the id
  names the model, not the content, and the reader's player-safe DOM contract
  is about board material). The reader has TWO premise branches — the generated
  reader and the spine checkpoint (a spine, no parts yet) — and BOTH carry the
  caption; only the first was pinned when the field landed, which is how the
  second shipped missing its prop, so a pin now covers each branch.
  The checkpoint's four `busy` controls — **Generate parts**, the retry-panel
  toggle, **Discard** and the retry panel's own run button — state why through
  the shared blocked-control device (§Why a control cannot act), in the same
  sentence the canvas uses for the same state ("The module is generating right
  now — wait for it (or press Stop)."), and its two at-an-end move buttons carry
  no reason (pinned). Measured, and reported rather than smoothed over
  (docs/17 row 99): the only production caller renders this branch solely when
  `parts.length === 0 && !busy`, so those four reasons are currently unreachable
  from that surface — the device is in place for the state the gate already
  encodes, not for a state that does not occur.
- **Module canvas** (owner decision, row 93 amendment — he asked for it
  explicitly: *"i do want to see who wrote the module text … please put it
  below the module text"*, reversing the arc's first "canvas excluded" call) —
  `canvas-preview-part-model-<n>` under each part in the PREVIEW, plus a footer
  strip `canvas-writer-model` below the editor (visible in both Edit and
  Preview) that names who wrote the module's text: one id when the premise and
  every part agree, and the per-scope list when they differ, with unrecorded
  scopes reading "not recorded". The strip reads the saved rows and sits
  OUTSIDE the editable document on purpose: that document IS the module text —
  it is saved to the parts and re-sent to models — so an id inside it would
  become model input (docs/18 §4).
- **Images** — the image lightbox caption, the module cover hero and the
  campaign cover art card. Small list-row thumbs and the 48px in-card portrait
  deliberately carry NO caption: the id would truncate to gibberish there, and
  every one of those surfaces also shows the same image at full size in a
  lightbox or the card banner, where it renders in full. Two more deliberate
  exclusions: the battle board / battlemap and its tokens (a player-facing
  surface — the table must not read model ids), and the workspace artifact
  editor's body (an authoring surface, where the owner is the writer). In the
  artifact editor's image lightbox the model is stated EXACTLY ONCE — the
  metadata line keeps dimensions/mime/source and the caption under the image
  carries the id, so the dialog never repeats it.

What the owner sees for real data: NOTHING at all when no model is recorded —
not an em dash, not a placeholder, not today's configured model. That covers
every upload, every hand-written artifact, and every text or image written
before this field existed (the three owner decisions are recorded in docs/17
row 93 and docs/18 §4). A hand edit does NOT remove an id: editing a part in
the reader, autosaving an artifact, attaching an image or renaming something
all leave the recorded writer in place, because the caption answers "which
model wrote this text", not "who touched it last" — a chat-applied rewrite or
an accepted refine proposal is the exception, and records the CHAT model,
because it really is the last writer of that text.

### Module reader — the writing-style bar

When the style a module RECORDED differs from that style's current text, a
one-line bar sits above the reader's body: *"This module is written in “House
Voice” v1; that style is now v2. Parts already written keep their text and
continue as they are."* with **Adopt v2** behind a confirmation that states
what it does and does not do (parts written from now on — and every retry,
repair or per-part regeneration — use the style's current text; parts already
written keep the text they have and are never rewritten by this; the module
records the new text), and **Keep v1** which dismisses the bar for the session
without writing anything. When the style was DELETED the bar only explains
itself (the module keeps its recorded text, so generation continues exactly as
before) and offers no adopt. When there is no difference — including every
module written before styles existed, which resolves to the immutable Classic —
the bar renders nothing at all.

### Part text editor (find/replace)

The ✎ affordance on a ready part (hidden otherwise) swaps that chapter to an
inline editor: the shared markdown textarea with a find/replace toolbar
above it — find with `active / total` match count, Enter/Shift+Enter and
prev/next buttons jumping the draft selection, an **Aa** case-sensitive
toggle, **Replace** (active match) + **Replace all**, a Preview toggle
rendering through the shared wiki-link pipeline, and **Save part** /
**Cancel**. Save persists to the module row with the `edited` flag and a
"Part saved" toast (blur also saves unless focus stays inside the editor);
Cancel discards without touching the row. A part saved this way shows the
hand-edited overwrite warning in the **Rewrite part** dialog, whose Cancel
is inert and whose confirm regenerates just that part.

### Stub generation ownership (integrity-fix arc)

The unresolved-chip popover's **Generate** runs the same chain machinery as
the batch, and its artifact is **module-owned from birth**: the chain step
carries `placementModuleId` (persisted on the run row, so pause/resume/retry
keeps it), and the post-run `stampModuleOwnership` call is the idempotent
`module:<title>` tag/history write only — ownership never depends on
surviving until after the run. If the owning module is deleted while a run is
in flight, the run FAILS loudly at finalize (failed run row + toast) instead
of creating an artifact owned by a module that no longer exists.

The popover's three actions — the verdict's **link** button, **Create stub** and
**Generate** — are held while a save from the popover runs, and each states why
through the shared blocked-control device (§Why a control cannot act) — "A save
from this popover is still running — wait for it to finish." — so a second press
can never begin a second write. The states that are self-evident carry no reason
and are pinned: an empty name is nothing to create, and **Generate** reads
"Generating…" while its own run is in flight.

### New Module dialog — automation grid

The "After the parts are written" grid carries the per-kind Generate/Image columns plus the "Generate encounter battlemaps" (default ON) and "Generate encounter mob images" (default OFF) toggles; after the parts finish, the sweep runs the checked automations — unresolved entities detailed, images queued, battlemaps and mob portraits for every roster participant that can own one — the encounter editor's own two lanes, so a chunk-backed creature shares the one canonically-cached bestiary portrait while every other participant (an uncited mob's on-demand creature, a materialized monster, a named NPC in the roster) gets its own local one (docs/08 §Post-generation automation, docs/17 row 96).

### New Module dialog — persisted draft and Advanced floor

Every value the dialog holds (concept included) is persisted to the settings row's `newModuleDraft`, tagged with the campaign, so a module creation can be retried after deleting the attempt or resetting the campaign without retyping: reopening the dialog in that campaign prefills it, and a draft written in another campaign is never prefilled there (nor overwritten). The save is debounced on change and flushed when the run starts, when the dialog closes and on unmount; **Reset to defaults** in the footer restores the dialog's defaults and replaces the stored draft. The two campaign wipes keep the draft deliberately — docs/08 §Creation UI, and the campaign-delete path clears it (docs/18 §2.1, the settings seam row).

Two guarantees hold the prefill together, and both are pinned by test:

- **The user's typing always wins.** The mark that says "this form is the user's" is set SYNCHRONOUSLY by the interaction itself (every field, toggle, stepper and reset), never by an effect. So the arriving prefill is skipped for the rest of that open the moment anything has been edited — including when the settings value lands in the very commit that carries the keystrokes (the shipped bug: the prefill ran first, wiped the typed prefix and the rest of the typing was appended to the wiped field). Once the form is the user's, no snapshot may overwrite it.
- **The row is the source of truth until then.** The prefill is re-applied while the form is still untouched, so a snapshot older than the stored draft — a close flushes the draft and that write needs a DB round trip, so a reopen can read the row before the write lands — is never the last word. Only the USER's edits are ever written back: an untouched form is never persisted, so a stale prefill can never be flushed over the draft it failed to show.
- A stored draft that no longer validates is scoped to the draft (docs/17 row 76): the dialog reports it once per open (`toastError`) and opens at its own defaults rather than half-prefilling from data the app cannot read.

**Writing style (docs/17 rows 86, 87 and 88).** The dialog carries a **Writing style** select listing the built-in styles (Classic, Story, Freestyle) and the user's own, and it defaults to the app default from Settings — which for a fresh app is **Freestyle** (row 88), so the select opens on Freestyle unless a stored default says otherwise. The app default decides only the style of a module that does not exist yet: a module that already recorded a style keeps composing from its own recorded copy, and a module that recorded none stays Classic by provenance (docs/08 §Default writing style). The choice rides the persisted draft like every other field — except that "no choice made" is stored as NO value, so the creation resolves the app default at the moment the module is created rather than freezing whichever style happened to be the default when the draft was written. Text under the select says what the style is and that the module records the text it used. An id that resolves to nothing (a style deleted in another tab) is named in place and creation refuses before a module row exists; a styles blob that cannot be read is reported in the dialog and only the built-ins are offered.

The **Advanced — encounter guardrails** disclosure holds the ONLY editable prompt guardrail: the encounter floor's on/off switch and its encounters-per-level number (docs/08 §Editable encounter floor). The number is written into the generation prompt and into the floor gate from one source of truth, and it is recorded ON THE MODULE ROW when the module is created, so that module's later repairs, rewrites and retries keep its own rules.

### Module deletion contract (Modules list → confirm dialog)

The confirm dialog shows the LIVE owned-artifact count and re-counts at
confirm time; the chosen branch (cascade / keep) applies to the rows that
exist at delete time — never to the count that was live when the dialog
opened, and never to a partial application (the whole disposal is one
transaction; a mid-cascade failure rolls everything back, module row
included). Deleting a module also aborts its in-flight spine/parts pass.
The contract: **in-flight runs fail loudly, already-finalized rows
cascade/release, nothing dangles.**

### Fresh-generation wipe (Edit campaign → danger zone)

**Remove all generated content…** deletes everything generation produced in
the campaign — every non-`pc` artifact (campaign- and module-owned, revisions
scrubbed through the artifact delete path), every module row, every battle,
and the campaign runs + deliverable outlines that would dangle into deleted
rows — so generation can restart clean while the Party (`pc` artifacts,
untouched with their revisions/images/links), the campaign row, settings,
personas and the global library survive. The deleted modules' saved document
versions (the Versions menu undo history, docs/08 §Simple undo) go WITH them
in the same transaction — a version describes a document whose module is
gone, so undo history is not kept content. The two-step confirm lists LIVE
counts by kind + module/battle counts and requires an explicit confirm (no
typing); the execute path re-lists everything inside ONE transaction (dialog
counts never decide what goes), so any failure rolls the whole wipe back
loudly — a partial wipe with a success toast is impossible. In-flight module
passes abort first; their runs fail loudly at finalize. The action lives in
the campaign settings surface only — never in the tree or another
high-traffic spot. For ONE region the tree's own per-region **remove all** is
the right rung instead (§Left pane — Campaign tree): it is campaign-scoped,
single-kind and cannot reach modules or the Party.

### Clear workspace (Edit campaign → danger zone)

**Clear workspace…** is the FULL per-campaign reset beside the wipe above:
everything under the campaign goes — every artifact of every kind
(INCLUDING the Party), every module row (parts, board canvas, chat threads
and the saved document versions behind them — the Versions menu undo
history, which goes with its module), every battle, run and deliverable
outline — while ONLY the campaign row itself (name, description, system —
the premise) stays, so generation restarts from a blank campaign. Rulebook
ingests (chunks/embeddings — global source material, expensive to rebuild),
the global library, personas and settings are never touched, and no other
campaign loses a row. The confirm dialog says so in as many words (it names
the saved versions among what is permanently deleted). The confirm types the
CAMPAIGN'S NAME (exact, case-sensitive — the multi-campaign footgun guard;
anything else refuses and deletes nothing), one clear runs at a time (a
second click while clearing refuses loudly), and the execute path re-lists
inside ONE transaction like the wipe. Afterwards a loud success toast names the cleared campaign; when
the user sits on deleted content (a module or campaign child route) the view
navigates out to the campaign page, now empty — every list already refreshed
through its Dexie live query, so no reload and no manual invalidation.

## Screen: Module canvas (`/c/:campaignId/m/:moduleId/canvas`)

Document co-authoring for the WHOLE module in ONE document
(08-MODULE-DESIGNER §Module canvas): a full-viewport module child surface
entered from the reader header (**Canvas**, beside **Board**) or the modules
list row (icon button). There is NO part selector — the editor holds every
planned part in plan order in the format the chat sees (the spine premise

keeps the text so it can be fixed). A generated SCENE BLOCK (08-MODULE-DESIGNER
§M4-B-2) is ordinary part text in this editor — heading, bold field labels and
bullets, all editable like any other prose — and the preview renders it through
the same `WikiMarkdown` the reader uses, so the canvas shows a scene block
exactly as the reader does. Editing inside a block never needs a special mode,
and the split-save, the session ledger and the durable Versions snapshots keep
its bytes untouched.

The editor is a CodeMirror 6 markdown document (GFM dialect): **the editor's
doc string IS the markdown** — byte-exact fidelity for `[[wiki-links]]`, code
and tables by construction, no WYSIWYG round-trip. `[[Name]]` tokens render
as kind-colored marks resolved against the reader pool (campaign + global
library) with the module's own tier-0 context — the exact `WikiMarkdown`
palette, unresolved dashed — and are ATOMIC (`[[Name]]` edits as one unit).
**Save** is ONE action for the whole document: only the parts whose text
changed land through THE one part-text save path (`edited: true`, promote
scan) exactly like the reader's hand edit; a failed part save names the
part loudly while the rest still lands.

A header with nothing to save shows a passive muted **Saved** chip (a check
icon and the word), never a disabled Save button: chat applies and accepted
proposals persist immediately, so after either the document already matches the
row and a permanently greyed-out control would read as broken or leftover
rather than as a state. The Save button is rendered only while the document
holds unsaved edits — enabled when idle, "Saving…" while a save is in flight,
and disabled with its reason stated through the shared blocked-control device
(§Why a control cannot act: "The module is generating right now — wait for it
(or press Stop)." / "Preview is read-only. Switch to Edit (the header toggle)
to save your edits.") while the module is generating or in read-only preview.
The chip is plain text, not a live region, so a save that settles announces
nothing on its own.

**Preview** (header toggle, session-only per module, OPEN BY DEFAULT on
first open): the canvas lands as chat + rendered preview side by side —
the preview fills its pane (padding kept, no centered narrow measure) while
the chat sidebar persists beside it, and the chat stays FULLY LIVE inside
it: sends run against the preview snapshot string (the editor is unmounted)
via the shared split + the existing per-part ladder, persist through the
existing split-save, and re-render the preview — with NO undo (no CM
history while the editor is unmounted; documented caveat, no UI apology).
Otherwise it renders the parts through the shared `WikiMarkdown` — the
reader's exact renderer with clickable entity chips (→ the peek modal),
separators and labels stripped, empty parts marked explicitly unwritten; a
broken scaffolding shows the splitter's loud reason instead of a render.
Save stays disabled in preview (there is no editor to save from); returning to
Edit remounts the editor from the latest snapshot through the existing
mountDoc path so unsaved edits and preview-applied edits survive. The last
chat replacement highlights in both surfaces (editor background mark, preview
an inline wash span — chat AND the two AI actions); deep links scroll the
preview articles when landing in preview. **Both AI actions WORK in the
preview** (docs/17 row 102): the preview is where the owner reads the module,
so nothing about it blocks them any more — Refine selection takes its span
from the rendered text (below), Rewrite part is unchanged, and both apply
through the same split-save the preview chat uses, with a durable pre-change
version. The gate they DO state is the honest one (generating / refine in
flight / open proposal), through the shared blocked-control device
(§Why a control cannot act).

**A rendered selection maps back to SOURCE, byte-exact or refuses.** "Refine
selection" in the preview resolves the browser selection to the exact markdown
bytes it will replace, and the confirm dialog SHOWS those bytes (a scrollable
source block) before anything can run — the safety property that makes a
rendered selection usable at all. The mapping walks the DOM (never geometry):
every rendered text run sits in a source-range span, and the resolver rebuilds
the run's pieces (its text nodes, and each wiki chip's `[[…]]` token) and
requires them to concatenate to exactly the source slice it claims. Refusals
are NAMED and never guessed — a selection inside a wiki chip says so and
suggests selecting the whole chip, a cross-part selection says one span in one
part, an unmappable span (inline code, an image, the unwritten-part
placeholder) says it is not mapped, a run whose text does not reproduce its
source says the range cannot be stated, and a capture from an older document
(old text) says to select again. Nothing runs on a refusal: the confirm is
held, and no model call is made. The same machinery is OPT-IN: the reader
passes nothing, renders byte-identically and carries no source attributes.

**AI actions** (one module = one generation, busy refuses loudly and never
queues): **Refine selection** replaces exactly the selected span — the model
gets the SELECTED range (plus enclosing block) and the instruction, never
the surrounding part — and **Rewrite part** proposes a whole-part rewrite of
an explicitly PICKED part (the dialog lists the plan; the cursor plays no
role). Both stream into a proposal overlay and stop supports the stream
(**Stop proposal**). Buttons are disabled while the module generates, a
proposal is in flight, or a whole-part proposal is pending — and each blocked
button STATES which of those it is, through the shared blocked-control device
(§Why a control cannot act), in the same order the gate reads them: "The
module is generating right now — wait for it (or press Stop)." / "A refine is
running." / "Accept or discard the pending proposal first."

**In Edit** the actions resolve their span from the editor and land as
PROPOSALS (accept/discard, one undo unit). **In Preview** there is no editor
and nothing to accept into, so the dialog's confirm applies the change
directly through the same split-save the preview chat uses — a durable
pre-change version first (Versions), then the row writes, then the snapshot
and the wash advance. The dialog is therefore the confirmation: it shows the
EXACT source text that will be replaced (both actions — for a rewrite it is
the picked part's whole text), Mode-dependent copy says which of the two
things the confirm does ("Apply" in preview, "Propose" in Edit), and the
toasts differ honestly: "Refinement applied" / "Rewrite applied" in preview,
"Proposal applied" after an Edit-mode accept.

**Proposals are decorations, never doc mutations** (TipTap suggestion-spec
pattern): a span proposal shows the original struck + the proposed text as a
green ghost with inline **Accept / Reject** controls at the range end
(disabled while streaming); a whole-part proposal renders NO-DIFF per the
board precedent — the NEW text as-is in the editor, **Show previous** flips
to the old text, and the header bar carries **Apply / Discard** (both held
while the replacement streams, stating "The proposal is still streaming — wait
for it, or press Stop proposal." through the shared device — the sentence names
the way out that is on the same bar). Typing
INSIDE a proposed range invalidates it with a loud toast (marimo semantics);
edits at the edges re-map the range instead. **Accept = one dispatch, one
undo unit** (Mod-y accepts the proposal at the cursor, Mod-u rejects it);
streaming chunks never enter undo history. Acceptance IS persistence: the
resulting text lands through the split-save (only the changed parts) and
appends the session **Versions** ledger per changed part (manual Save
appends "you" entries the same way). Leaving the page with a pending proposal
or unsaved edits demands an explicit "Discard and leave" confirm (deep links
and the preview toggle never guard — the doc is one document).

**Versions menu — the simple undo** (owner-directed, docs/08 §Simple undo,

each other. The destructive **Clear all previous versions** item sits in the

auto-opens again. Auto-open fires once per browser and only when campaigns ==
0 (an upgraded install is never hijacked). Re-open affordances: picker header
"Get set up" + empty-card "Set up Campaigner" button, the workspace welcome
panel, and the help **setup** topic's "Reopen the setup wizard" action. All
hidden once complete (picker/welcome; help topic stays).

### Screen: First-module guide (`/guide`, `/guide/:chapterId`)

A full-page in-app route authored as structured data (`guideContent.ts`,
helpContent pattern) and opened **in another tab** (`target="_blank"`) from
the wizard's last step, the help setup topic and the modules empty state — a
same-origin tab keeps IndexedDB, so it can deep-link the reader's own
campaign. Nine chapters teach the authored path: start here → campaign →
rules & pins → create module → approve the spine → read/edit/rewrite →
resolve the cast → battlemaps → table & print. Each chapter ends with a
checkpoint line and a "Do it now" button: static routes always resolve;
campaign-scoped ones resolve against the most recently updated campaign and
render as a disabled hint while none exists. A test guarantees content
completeness and that every app link's route exists in the route table.

## Top bar — generation language

The top bar carries a language select (globe icon) on every route, including
the main page: it picks the language all generation prompts must produce
(default English) and persists it in the settings row (`language`). The same
control appears on the Settings page.

## Screen: Deliverable builder (`/c/:campaignId/deliverables`) — M3-D

Left: deliverable list (+ create). Right: outline editor — nested chapters /
parts / artifacts / text / galleries with add and up/down/remove buttons (no
drag-and-drop libs), per-artifact include toggles (body / data / stat blocks /
images), audience switch (GM / Player), and a cover image picker over campaign
images. "Generate PDF" renders via pdfmake (cover, ToC, chapter banners with
kickers, read-aloud boxes, two-column stat boxes, ≤45%-width images, NPC
gallery + treasure ledger appendices) and downloads the file. "Seed from
module" maps premise and parts plus resolved owned entities. Module-owned

user explicitly adds its artifact node—never through seeding or an automatic
gallery/ledger.
