# 05 — UI Specification

Tailwind + shadcn/ui, dark mode default (GM-at-the-table friendly), light mode
toggle in the top bar. Routing via react-router.

## Routes

```
/                              → campaign picker
/c/:campaignId                 → three-pane workspace
/c/:campaignId/a/:artifactId   → workspace with artifact open
/c/:campaignId/graph           → link graph
/c/:campaignId/modules         → module list
/c/:campaignId/m/:moduleId     → module reader (the only play view)
/c/:campaignId/m/:moduleId/battle → module's live battle table
/c/:campaignId/deliverables    → deliverable builder
/rules                         → rules library
/settings                      → settings
/guide                         → first-module guide (chapter 1)
/guide/:chapterId              → one guide chapter (opens in another tab)
```

Top bar: app name, campaign switcher, Rules / Settings navigation, the
last-module shortcut (arrow + the name of the module whose reader was opened
last, one click back to it — hidden until a reader has been opened), New
Module on campaign routes, Ctrl+K quick-find, generation language, help and
theme. Directly below it, the **campaign bar** renders the campaign-level tabs —
Modules / Workspace / Deliverables / Graph, Modules first (the central view
the rest feeds) — on every route, disabled (with an
"Open a campaign first" hint) while no campaign is open. On nested screens the
bar's right side shows a breadcrumb (Campaigns / Modules / *module title* / Battle
table), so deep screens always state where they are and exit in one click.
The retired `/play` route and `▶ Play` button do not exist.

### Quick-find (Ctrl+K)

The palette follows the workspace scope preference. Artifact hits search
name/tags/summary/aliases; global hits are labeled **Library**. Module/part and rule
hits share the palette. Enter navigates to an artifact or module; rule hits
open an inline preview with **Pin to Assistant**. With an empty query the
palette lists a **Go to** group — the campaign sections (Workspace, Modules,
Deliverables, Graph), Rules and Settings, and **Battle table (this module)**
on a module reader screen — so Ctrl+K doubles as an app map.

## Progress dock

The app-wide dock reports every slow task (batch generation, module parts,
PDF builds). Its header hosts **Stop all**, which sweeps every running
generation (job queues, in-flight runs, the module forge, a running chain) —
non-destructive, stopped runs stay resumable. Jobs that live somewhere (a persona run, a module mid-forge)
render their label as an **Open** button that navigates to the job — a run
opens preselected in the workspace persona panel (`?run=`), a module opens in
its reader. A module that is being forged also shows the live step ("Writing
part 2 of 5: …") on its Modules list row.

## Screen: Module reader (`/c/:campaignId/m/:moduleId`) — M6

The module reader is the only play view: table of contents/search on the left,
adventure prose and wiki-link chips in the center, entity panel on the right.
Its shared Library / Campaign / Module scope control defaults to all scopes.
**Battle table** opens the module's live board — offered both in the reader
header (a mode change, visible even with the contents sidebar collapsed) and
in the contents sidebar. Encounter rows offer **Run battle**. Module-owned
rows can be adopted back into the campaign. Recorded
encounter entities can be batch-detailed, and **Generate encounter maps** runs
a one-candidate unattended queue for module encounters still lacking layouts;
failures remain retryable and do not stop later jobs.

### Stub generation ownership (integrity-fix arc)

The unresolved-chip popover's **Generate** runs the same chain machinery as
the batch, and its artifact is **module-owned from birth**: the chain step
carries `placementModuleId` (persisted on the run row, so pause/resume/retry
keeps it), and the post-run `stampModuleOwnership` call is the idempotent
`module:<title>` tag/history write only — ownership never depends on
surviving until after the run. If the owning module is deleted while a run is
in flight, the run FAILS loudly at finalize (failed run row + toast) instead
of creating an artifact owned by a module that no longer exists.

### Module deletion contract (Modules list → confirm dialog)

The confirm dialog shows the LIVE owned-artifact count and re-counts at
confirm time; the chosen branch (cascade / keep) applies to the rows that
exist at delete time — never to the count that was live when the dialog
opened, and never to a partial application (the whole disposal is one
transaction; a mid-cascade failure rolls everything back, module row
included). Deleting a module also aborts its in-flight spine/parts pass.
The contract: **in-flight runs fail loudly, already-finalized rows
cascade/release, nothing dangles.**

### Fresh-generation wipe (Edit campaign → danger zone)

**Remove all generated content…** deletes everything generation produced in
the campaign — every non-`pc` artifact (campaign- and module-owned, revisions
scrubbed through the artifact delete path), every module row, every battle,
and the campaign runs + deliverable outlines that would dangle into deleted
rows — so generation can restart clean while the Party (`pc` artifacts,
untouched with their revisions/images/links), the campaign row, settings,
personas and the global library survive. The two-step confirm lists LIVE
counts by kind + module/battle counts and requires an explicit confirm (no
typing); the execute path re-lists everything inside ONE transaction (dialog
counts never decide what goes), so any failure rolls the whole wipe back
loudly — a partial wipe with a success toast is impossible. In-flight module
passes abort first; their runs fail loudly at finalize. The action lives in
the campaign settings surface only — never in the tree or another
high-traffic spot.

## Screen: Battle table (`/c/:campaignId/m/:moduleId/battle`) — M6-E

Full-screen dark board rendered from one module-anchored battle row. Seeding
an encounter replaces that module's prior live board after confirmation;
**Back to module** exits the surface to the module reader (a direct link, not
history-dependent). `data-player-safe="true"` marks Player view. Amended
2026-09-06 (encounter-resume arc): *reopening the battle table resumes the
persisted board verbatim — positions, HP, veils, initiative, stage snapshot
and per-token visibility all survive a Lift → re-enter cycle; the first-entry
token reveal (`everLive`) is spent once per seed, so the GM's hidden tokens
stay hidden across reopenings. The toolbar also carries a destructive
two-step **Re-seed** (provenance-bearing battles, GM mode) that replaces the
running board from the row's own provenance encounter, and the GM-view rail
shows the provenance line ("Seeded from …", plus "Re-seeded <when> from …"
after a replace; a deleted seeding encounter says so, never blank). The rail
also carries a GM-only **Spawn** panel: the provenance encounter's roster as
a readout (names × count) plus ONE **Spawn** button opening the spawn picker —
three groups (this encounter's roster, campaign NPCs, core rulebook mobs)
behind one name search and a name/level sort toggle (missing or unparsable
levels sort last). Roster picks spawn through `spawnRosterInstance` (the same
provenance path as before); NPC and core-mob picks spawn a single instance
through the shared `expandRosterEntries` expansion (npc-ref by reference, one
get-or-created mob artifact per cited chunk, one frozen seed row). Every pick
lands on a free spot near the board center (never stacked atop an existing
token), labels continue the on-board count, statless picks badge loudly, and
with initiative on the latecomer is auto-rolled — mid-fight reinforcements
without re-seeding. Player-safe mode shows no Spawn button, as before.*

The DOM carries only board-safe material: map, grid, staging ground, visible
tokens, HP meters, veils/fog, effect markers (D8 — disc/square showpieces at
~70% transparent fill, rendered in BOTH views), initiative and toolbar—never
stat text, notes or secrets. Veiled mob tokens are removed from the DOM in player view (coverage
hides mobs only — PCs and other tokens are never coverage-hidden and render
above the veil), `visible: false` tokens in both views. Amended 2026-09-06 by
8fa7abd: *veils previously removed any overlapping token in both views at
~100% opacity; veils now tint the map ~10% in both views (selection reads via
outline, not opacity) and coverage hides mob tokens only — the GM view sees
everything under its own veils.* Drag commits once
on release — moves bubble to the board so a drag that leaves the piece node
mid-gesture keeps tracking, and an off-piece release finishes with the same
commit/tap-select semantics (never a leaked lift or snap-back); tap edits
HP/visibility/scale; map pan/zoom, fog tools, stage reset
and initiative remain. In GM view, selecting a mob also shows its full stat
block in the right rail; the rail widens for the stat block. Player view never
mounts this stat block or its source text. NPC HP is token-owned; PC HP persists
on the campaign PC artifact. Amended 2026-09-06 by 4e3de75: *HP editing is button-only —
quick ± steppers (Damage −10/−5/−1, Heal +1/+5/+10, ≥44px targets) apply
clamped deltas directly, and Roll damage / Roll heal open the reusable dice
roller (`src/features/dice/DiceRoller`, 3D engine lazy-loaded on first open,

Generated layouts stamp normalized rows/columns on the board. Grid tracks,
snapping, fog resizing/coverage and token size derive from those cells on every
viewport. One fog veil covers each room's mob rectangle; room mobs begin

spawn inside the entry-room rectangle. Uploaded maps with no layout retain the
legacy pixel-grid behavior. Amended 2026-09-08 by the site-shape arc
(docs/11 D11/D13): *the party's spawn room never gets a veil — a SINGLE
site ("Encounter") seeds zero veils and starts straight at the entrance cell
(else the mob-area center), while a COMPLEX ("Dungeon") plays sequentially:
the GM rail gains a Dungeon Path list (rooms in stored path order, the
revealed frontier highlighted) with a "Reveal next room" button that lifts
the next veiled room's veil — an advisory aid only: no locks, no initiative
resets. Room-key markers sit at each room's mob-area center.* Amended 2026-09-06 by cbe8218: *panning starts
from the map image and content background too — a pointer-down on the map was
previously a dead zone that only the letterbox escaped.*

## Screen: Campaign picker (`/`)

Card grid of campaigns (name, description snippet — line-clamped, shown only
when set —, system badge, artifact count, updatedAt) + "New Campaign" card →
dialog with name, system select (`GameSystem` values), description textarea.
The card menu offers **Edit campaign…** — a small dialog for name and
description (empty description is valid) plus the **Remove all generated
content…** danger zone (fresh-generation wipe, above); the game system is
shown read-only
because stat blocks and battles depend on it. Delete via card menu with
confirm dialog (cascades: artifacts, revisions, runs). Opening a campaign —
card click or top-bar switcher — lands on its **Modules** view (the central
view); that landing's header repeats the campaign name + description (muted,
clamped, only when set) and carries the same **Edit campaign** affordance.

## Screen: Workspace (`/c/:campaignId`) — the main three-pane layout

Resizable panes (shadcn `resizable`), min widths 200 / 360 / 280 px
(840 total — the default 22/48/30 layout clears every floor at 1024px iPad
landscape, and the orientation gate blocks anything under ~960px). The right
(persona) pane is collapsible via drag so cramped screens can reclaim it; the
tree and editor never collapse. Campaign tree rows reach 44px on coarse
pointers (`pointer-coarse:min-h-11`, desktop rows unchanged).

### Left pane — Campaign tree
- Header scope control: Library / Campaign / Module, persisted in settings.
  Workspace defaults to Campaign + Module; Library starts off.
- Library rows appear only in the dedicated **Library** group. Module-owned
  rows appear under their module; remaining rows use kind groups. A
  module-owned row whose module row is missing renders in an explicit
  **Orphaned** group (amber `orphaned` badge per row) — never silently
  blended into the kind groups — with a one-click **Re-anchor to campaign**
  context action (`adoptIntoCampaign`/moveScope) as the sanctioned fix.
- Rows show name, summary tooltip and active state. Filter matches name/tags.
- Context menus include rename/delete and explicit ownership transitions:
  eligible kinds can be published to Library after a loud shared-content
  confirmation; global rows can be adopted into a selected campaign.

### Center pane — Artifact editor
- Header: editable name, kind and revision badges, ownership actions, and a
  prominent amber **Library** badge for shared Library rows. Module-owned
  rows show an **Open in module** link into the module reader (the inverse of
  the peek modal's "Open in workspace"). The
  revision indicator ("rev 7") opens a dropdown listing revisions
  (timestamp + source); selecting one shows read-only snapshot with a
  "Restore this revision" button (restore = save as new revision).
- Run battle (encounters): an encounter open in the editor can seed a battle
  without opening the module reader. A module-owned encounter shows **Run
  battle** anchored to its own module; a campaign- or Library-scoped
  encounter shows **Run battle…**, which opens a minimal picker over the
  campaign's modules (title + artifact count, arrow-key navigable; with no
  modules it shows a named empty state explaining that battles anchor to
  modules). Both paths reuse the module view's `RunBattleButton` and its
  two-step "Replace running battle?" confirm — seeding still anchors per
  module (10-MILESTONE-6 D10) and replaces a running board only after
  confirmation. Amended 2026-09-06 (encounter-resume arc, resume-by-default):
  *a module whose running battle was seeded from THIS encounter shows
  **Open battle** instead — a plain navigation that reattaches the persisted
  board without touching it; re-seeding the same encounter becomes the
  explicit two-step **Re-run battle** → "Replace running battle?" path. A
  battle from a different encounter (or with no provenance) keeps the old
  confirm-first replace flow, and the picker's rows follow the same split.*
- Aliases: an "Also known as" chip input directly below the tags row in the
  header (all kinds — 08-MODULE-DESIGNER M4-A). Enter or comma adds, ×
  removes. Input is trimmed; empty input is ignored; duplicates — and an
  alias equal to the artifact's own name — are rejected case-insensitively
  (`resolveWikiLink` matches the name first, so such an alias could never
  resolve). Stored spelling is preserved verbatim; resolution lowercases on
  its own. Removing an alias never rewrites module text: a prose `[[Name]]`
  that only matched via the removed alias simply becomes an unresolved
  wiki-link, handled by the existing stub/adopt flow.
- Body: markdown editor for `body` — plain `<textarea>` with a Preview toggle
  rendering via `react-markdown`. **No WYSIWYG editor in M1.**
- Kind-specific form below the body, plain labeled inputs mapped 1:1 to the
  `data` fields from 01-DATA-MODEL (e.g. NPC: appearance, personality;
  pointsOfInterest/ranks as add/remove row lists).
- Stat block (NPC): rendered as a classic stat-block card (name line, AC/HP/
  Speed row, ability score grid, traits/actions lists) with an "Edit" toggle
  switching to a form. "Remove stat block" / "Add stat block" buttons.
- Links section: list of `relation → target name` rows (target is a
  combobox over campaign artifacts), add/remove.
- Mentions section ("Mentioned in", 14-BACKLINKS-ORPHANS): read-only
  panel directly below the Links section listing every wiki-link mention
  of this entity across all modules — one row per (module, document)
  with module title, Premise/Part N and ×count, each row deep-linking to
  the reader location. Alias-only matches merge in (a "Mentioned as"
  line names the spellings); an ambiguous winner shows ⚠. Wiki-link
  mentions only — curated relations stay in the Links section above.
  Derived at read time, uncapped, nothing persisted.
- Encounter Battlemap section: upload/select a map or launch **Generate layout
  & map**. When a map is on file the section shows a clickable preview
  thumbnail plus the room count of the stored layout; the action button reads
  **Regenerate**. Regenerate hands the existing artifact to Encounter
  Cartographer; identity, prose, links and roster stay fixed while layout/map
  are replaced. The pre-filled brief in the persona panel says "Generate…" for
  a mapless encounter and "Regenerate…" only when a map already exists.
- Encounter room keys & mob treasure (room-keys/treasure arc, 2026-09-07):
  the encounter form's Monsters rows each gain a "Treasure carried by one of
  these" textarea (what ONE instance carries — frozen onto each seeded
  battle token); when a battlemap layout exists a **Room keys** section
  lists one key + room-treasure textarea per room, labelled
  `Room <letter> — <name>`; edits touch only the key fields. The battlemap
  section notes that **regenerating the layout & map writes fresh room
  keys** — the accepted consequence of D9 (11-ENCOUNTER-GENERATOR).
  Amended 2026-09-08 by the site-shape arc (docs/11 D11/D12): *the Room
  keys section lists complexes in PATH order with up/down controls that
  rewrite only `layout.path` (the rooms array — rects and keys — never
  reorders), and each room gains a target-level input (the per-room
  challenge target; the budget loop may lower it a step and the final
  value stays owner-editable). The form also shows the budget loop's
  advisory (top of the form) — legacy migrated complexes display their
  under-budget note here. A Site-shape select sits beside Location kind,
  labelled **Encounter (single)** / **Dungeon (complex)**; the option the
  battlemap on file cannot hold is disabled with the reason in the hint.*
- Encounter mob portraits (mob-artifact arc, 11-ENCOUNTER-GENERATOR D5
  amendment): below the roster form a portraits section shows the
  **Generate mob portraits** batch (one cover portrait per rulebook-cited
  creature kind, shared on the battle board) plus — for uncited entries
  (`inline` / `none`) — a per-entry **Create creature + portrait** row
  (origin badge: "invented, with stat block" / "invented, name only").
  With zero rulebook entries the batch stays enabled as
  **Create creatures + portraits** (batch-all for the invented rows); with
  no roster entries at all it disables with a no-creatures message. All
  generation here is GM-only (the editor never mounts in player-safe view);
  failures toast loudly per entry.
- Saving: autosave with 800 ms debounce; every autosave that changed content
  creates a revision. Show "Saved" / "Saving…" text near the header.

### Right pane — Persona panel (tabs: **Assistant** | **Runs**)

**Assistant tab**
- Persona select (dropdown of personas), autonomy select
  (Manual / Review / Auto, default Manual), brief textarea, "Pinned rules"
  list (added from Rules browser; removable chips), Start button
  (disabled without API key → hint linking to Settings).
- **Module** select (generate/encounter personas creating a NEW artifact
  only; hidden when the run targets an existing one — an in-place fill's
  placement is immutable outside the editor's explicit scope moves). The
  choice is one-off per run, default **"Campaign (no module)"**; choosing a
  module shows "The created {npc} will live in module “{title}”." and the
  created artifact is owned by that module (`moduleId`, M6-A semantics).
- **After creation** extras checkboxes, derived from the CHOSEN persona
  (`postCreateExtras` declared on the persona, else derived from
  `mode`/`producesKind` — src/llm/personas/extras.ts): **"Generate a cover
  image"** (all kinds), **"Include a stat block"** (npc personas;
  verification-only — a finished run whose created artifact has no stat
  block shows the persisted finalize notice "No stat block was generated —
  add one in the artifact editor.") and **"Generate mob portraits"**
  (encounter personas). image/statBlock/mobPortraits persist as remembered
  defaults in Settings → `runExtras` (same pattern as the map aspect).
  Extras execute AFTER the run completes, in the shared unattended queues —
  a completed run is never reopened or failed by them; per-artifact failures
  toast loudly.
- **Automatic battlemaps** (D10 amendment arc): the former one-off
  "Generate a battlemap" extra is GONE — every run that freshly CREATES an
  encounter artifact (persona panel, entity batch, module post-generation)
  gets its battlemap enqueued automatically on the unattended encounter-map
  queue with the campaign's defaults (aspect from Settings, preset resolved
  through the encounter's own locationKind — 11 §D10 amendment). Skipped
  for regenerations (an existing map is preserved; a new map is an explicit
  user action), for Cartographer runs (they map in-run), for already-mapped
  or already-queued encounters (the no-double-work guard), and for
  encounters of modules whose "Generate encounter battlemaps" master switch
  is off. Queue failures toast loudly per artifact and never fail the
  finished run.
- Active run view: vertical step list (retrieve / draft / statblock /
  finalize) with status icons; a global target repeats the **Global** warning
  badge. The running step shows streamed tokens in a monospace scroll area.
- On `awaiting_user`: step card shows the parsed output rendered nicely
  (draft = the NPC fields; retrieve = chunk list with checkboxes to drop
  chunks) with buttons **Approve**, **Edit** (opens a JSON/text editor for the
  step output), **Retry…** (optional instruction input), **Cancel run**.
- Encounter Cartographer adds a persisted 4:3 / 16:9 / 1:1 aspect select
  and a persisted Auto / Standard / Dungeon preset select — **Auto is the
  default** (D10 amendment): each encounter's own locationKind decides its
  tier, Standard/Dungeon force it; a regenerate keeps the target encounter's
  own preset (11-ENCOUNTER-GENERATOR D10).
  Brief and layout checkpoints are editable; layout review shows labeled room
  and mob rectangles. Candidate maps carry the same overlay, and exactly one
  map is selected; the pick view carries **Regenerate candidates** (docs/11
  D14 — re-runs the stylize step only: same brief and layout, room keys
  untouched, a fresh batch lands in the same pick pause). Auto mode picks
  candidate one.
- On completion: success banner with "Open artifact" button.
- On failure: the failed-run card keeps the recovery row — **Resume
  generation**, **Resume with instruction…**, **Dismiss** — and adds a
  **Details** disclosure (chevron, not a modal): the failure-classification
  badge with a one-line guidance sentence per kind, the step the run died on
  (the same step resuming restarts from), started/failed timestamps, and the
  FULL raw `errorMessage` in a select-text mono block with a **Copy** button
  (when the clipboard is unavailable — e.g. insecure contexts — a loud note
  says to select the text manually; the block stays selectable). The
  classification (`failureKind` on the run row: congestion / filter /
  schema-rejected / invalid-output / bug / cancelled / unknown) only
  ANNOTATES the message, never replaces or truncates it; legacy rows without
  a kind render the 'unknown' guidance — no migration. The Runs tab's
  open-run report shows the same Details section for failed runs.

**Runs tab** — table of past runs (persona, brief truncated, status,
updatedAt); clicking shows the read-only step log; failed runs include the
failed-run Details section described above (classification + guidance + raw
error).

**Writers' room tab — module forge progress visibility**
- While the forge runs, a status line reads
  `Generating module — step X of Y: <step title>` (refinement phase reads
  `Refinement pass — …`).
- The step plan is listed with human-readable titles (Plot arc, Session 1,
  Key location 1, …, Continuity review, Refine: "<artifact>") and per-step
  state badges.
- Finished steps name the artifact they produced (`→ <artifact name>`).
- The currently running step shows a live tail of the streamed tokens
  (monospace preview, last ~400 chars).
- When a step fails (LLM error, invalid JSON after retry), the forge does
  **not** restart: a `Retry failed step` button re-runs only the failed step
  as a new run, feeding it the artifacts of every completed step before it,
  then continues the remaining plan (including the refinement pass when the
  generation phase completed). The failed run stays in the Runs tab with its
  error message. The chain builder has the same retry affordance.

## Screen: Rules (`/rules`)

Two-pane:
- Left: book list (title, system badge, status chip incl. processing progress
  bar, chunk count, menu: Rename / Set system / "Embed whole book" / Delete)
  + "Import PDFs" button (multi-file input).
- Right: a tab strip — **Search** (default) and **Bestiary**. Search is the
  box (searches on Enter / 300 ms debounce), filters (book multi-select,
  chunkType checkboxes), result list: heading path as breadcrumb, book + page
  badge, text snippet with highlighted terms, source badge (kw/sem/both).
  Clicking a result expands the full chunk text (stat blocks render with the
  stat-block card). Each result has a **"Pin to Assistant"** button (adds to a
  global zustand pin list consumed by the persona panel; toast confirms).
- The **Bestiary tab** (see 12-BESTIARY-PACKS §12) is a player-safe roster
  viewer: name filter + system select over every ready book's stat-block
  chunks, virtualized (level-ordered), with a StatBlockCard detail pane and
  origin labels; pack chunks violating the exactness invariant appear as loud
  data-error rows pinned to the top. The detail pane's **"Spawn into module"**
  opens a campaign/module picker (single campaign preselects itself; zero
  campaigns/modules are named empty states) and toasts
  `"<creature> spawned into '<module>'"` with an **Open module** action.

### Bestiary packs (delta for 12-BESTIARY-PACKS §6/§8)

- Next to "Import PDFs" a second **"Import bestiary pack"** button opens a
  dialog: adapter select (registered adapters only), a multi-file input
  (`.json` / `.db` / `.yml` / `.zip`), then the import report — imported /
  skipped / failed counts with an expandable failed-entries list. While the
  import runs, the new book's processing chip reports done/total progress
  exactly like PDF page progress; a zero-entry import ends in a loud
  `error` book + toast (no empty ready book).
- Pack book cards carry a **Pack** badge, and the book menu gains a
  **License** item showing `packMeta.license` verbatim.
- Monster entries resolved from a pack chunk print the origin label
  `"<bookTitle>: <creatureName>"` instead of a page number (packs have no
  pages); PDF chunks keep `"<bookTitle> p.<pageStart>"`.

### PDF viewer (delta; retained-bytes source viewing)

- PDF-origin book cards carry a **View PDF** button; every search hit
  carries **"Open at p. N"** (the chunk→page jump; reliable for PDF books
  only — pack chunks are stubbed to page 1). Either swaps the
  right pane to the in-app PDF viewer (canvas render via `pdfjs-dist`, one
  shared worker wiring in `src/lib/pdfRuntime`, fit-width + zoom, page nav)
  opened at the requested page; "Library" goes back (the viewer is pane
  state, not a route).
- A book without retained bytes (`pdfFiles` row absent — ingested before
  retention) shows the **loud absent state** naming the cause and the
  remedy: delete the book and import the PDF again. There is deliberately
  NO attach affordance — retention happens at ingest or not at all
  (owner-ratified cut of re-attach). Text-layer selection and
  cMaps/standard-fonts assets are documented fast-follows; v1 is
  canvas-only.

## Screen: Settings (`/settings`)

- OpenRouter API key (password input, "Test key" button calling
  `GET /api/v1/models` and reporting ok/fail).
- **First-try chat model** (workhorse; cheaper is fine) + **Fallback chat
  model** (escalation tier — used on congestion, content refusal, or one
  contract-repair attempt; empty = no fallback and failures stay loud) +
  embedding model (text inputs with the defaults from 01-DATA-MODEL
  prefilled; below each a combobox of models fetched from `/models` when key
  is valid).
- Embeddings enabled toggle.
- **Parallel requests** (1–4, default 2): how many INDEPENDENT generation
  requests run at once — entity batch runs, background image-queue jobs.
  Dependent chains (module parts, writers' room)
  stay sequential regardless of this setting. Free OpenRouter models cap at
  20 requests/minute, so keep the level low when using `:free` models.
- Image generation section (M3-A): enabled toggle; **First-try image model**
  and **Fallback image model** (browse lists filtered to
  `output_modalities=image`; the fallback runs only when the first-try model
  is congested or refuses). (The former "Encounter map verify model" setting
  was removed with the verify step — docs/11 D14.)
- Appearance (UI scale): a four-step select — 90% / 100% (default) / 110% /
  125% — that scales controls and text app-wide; battle-map boards and 3D
  dice are unaffected. The choice is a device display preference persisted in
  localStorage (`campaigner.uiScale`, riding the theme's pattern — never in
  the settings row, so it stays out of the data DB and backups) and survives
  Delete-all-data like the theme. Mechanism: a `--ui-scale` CSS var (default
  1) multiplied into the root font-size — the app is rem-based, so one var
  scales spacing/text/radii — applied app-wide by `useUiScaleSync` in the
  shell. Deliberately NOT CSS zoom (it breaks board/pointer px math and
  Firefox); the intentionally fixed-px surfaces are listed in
  18-ARCHITECTURE §4.
- Personas section: list of personas; expanding one shows editable name,
  description, model (blank = default), temperature slider, system prompt
  textarea; "Reset to default" for built-ins.
- Backup & restore (M4-C): "Save everything" zips the ENTIRE IndexedDB state
  (all campaigns, artifacts, rulebooks, chunks, embeddings, personas, runs,
  deliverables, modules, images) into `campaigner-backup-<date>.zip`;
  "Load everything" restores one, REPLACING all current data after a confirm
  dialog. The OpenRouter API key never leaves the browser: it is stripped
  from saves and the locally stored key survives restores. Browsers with the
  File System Access API get native save/open dialogs; the rest fall back to
  a plain download and a file input. The save destination is acquired
  FIRST, inside the click's user-gesture window, and the zip is written to
  it after the build — the native picker requires transient activation,
  which a large backup build would otherwise outlive.
  Retained rulebook PDF bytes are EXCLUDED always (source-viewers arc,
  2026-09-05 owner ratification — the PDF is a convenience copy of a file
  the user owns on disk; chunks/embeddings carry the functional data). When
  books carry retained PDFs, a loud destructive note above the save button
  states the count and ~size and points at re-import after a restore; the
  note renders before the save, never as a post-hoc toast. Pre-retention
  backups (zips without the `pdfFiles` table) still restore — the table is
  optional in the restore's missing-table check and lands empty.
- Storage persistence status line: shows whether the browser committed to
  keeping the IndexedDB (`navigator.storage.persist()` is requested on app
  start); hints at home-screen installation when storage is best-effort.
- Danger zone: "Delete all data" (confirm by typing DELETE).

## Tablet & PWA support (landscape-first)

Campaigner is a dense landscape workspace (~840px pane minimums); portrait
and narrow viewports are unsupported by design.

- Orientation gate: pure-CSS hard blocks rendered by the app shell —
  `orientation-gate.tsx` shows a rotate prompt on any portrait viewport and a
  "screen too narrow" message on landscape viewports under ~960px (iPhone,
  Split View). Applies in the browser tab and installed alike: WebKit
  supports neither the manifest `orientation` member nor
  `screen.orientation.lock()`, so the overlay is the only real enforcement.
- Installable PWA: `public/manifest.webmanifest` (standalone, landscape,
  relative entry points so non-root Vite bases work), PNG icons generated
  from `favicon.svg` (incl. a maskable variant), and `public/sw.js` caching
  the app shell — network-first for navigations with an offline fallback,
  cache-first for hashed `/assets/`, cross-origin and non-GET requests
  (OpenRouter) untouched. Registered production-only from `main.tsx`.
- Home-screen installation is the strongly preferred mode on iPad: standalone
  window, and WebKit exempts installed home-screen web apps from ITP's 7-day
  script-writable-storage cap (data eviction) — verified against
  webkit.org's tracking-prevention policy. iOS has no programmatic install
  prompt, so a one-time hint (`install-hint.tsx`) explains
  Share → Add to Home Screen on touch devices running as a browser tab;
  dismissal persists in localStorage.
- Safe areas: the shell frame pads with `env(safe-area-inset-*)` on all four
  sides (top/left/right plus bottom, so content clears the home indicator
  when the ProgressDock is empty) while the Toaster and ProgressDock keep
  their own bottom offsets exactly once (fixed layers ignore the frame pad —
  no double-padding); dialog content clamps to `max-h-[calc(100dvh-2rem)]`
  with scroll so short-landscape dialogs never clip under the URL bar.
- Touch behavior: interactive elements opt out of double-tap zoom
  (`touch-action: manipulation` on buttons, links, `[role=button]`, summaries,
  select/tab/context-menu triggers — pinch zoom stays available); Buttons grow
  their hit box via a `pointer: coarse` pseudo-element (±6px pad, so a 32px
  button reaches the 44px finger target with no visual or layout change) while
  the sub-32px button sizes (xs/sm/icon-xs/icon-sm, incl. the dialog close
  button) carry a 44px coarse-pointer minimum; checkbox, resizable-handle and
  tab triggers likewise reach 44px on coarse pointers (transparent hit pads /
  44px tab row, visuals unchanged); hover-revealed controls (tree-row and run delete buttons)
  render permanently on coarse pointers; quick find has a top-bar button —
  the Ctrl/Cmd+K hotkey is unreachable on an on-screen keyboard.
- Fullscreen image gestures (`zoomable-image.tsx`): pinch zoom anchored on
  the gesture midpoint, one-finger pan clamped to the scaled overflow,
  double-tap toggles 2.5×, wheel zooms with a pointer, tap closes at fit
  scale (deferred past the double-tap window), plus an explicit close button.
- Startup images: `scripts/generate-splash.mjs` emits a solid
  `background_color` fill per iPad class × orientation × pixel ratio
  (`public/splash/`), linked from `index.html`; `apple-mobile-web-app-capable`
  plus the modern `mobile-web-app-capable`, `apple-mobile-web-app-title`,
  and `apple-mobile-web-app-status-bar-style: black-translucent` cover
  pre-manifest iPadOS and the full-bleed status bar. The viewport stays
  zoomable (no maximum-scale / user-scalable=no). WebKit accepts a splash
  only on an exact media match — the `pwa-assets` test parses each link and
  asserts the PNG's IHDR dimensions, so a mismatch fails CI.

## Onboarding (setup wizard + first-module guide) — M-onboarding

### Screen: Setup wizard (dialog, all routes)

A first-run **welcome + setup wizard** mounted once in the AppShell (like the
help dialog) and backed by the settings row's `onboarding` field:
`status: fresh | active | dismissed | complete` plus per-step entries
(missing = pending). A checklist, not a stepper — six steps that link OUT to
the surfaces that already do the work:

1. **Welcome** (in-dialog): what Campaigner is, local-first, the key is a paid
   service. Resolves on **Begin**.
2. **OpenRouter key** → Settings. Auto-ticks when a key is saved. Copy states
   what the key is, that OpenRouter is paid (≈$3/M tokens default model, a few
   cents per run), where to get one (openrouter.ai/keys), and that the key is
   stored only in this browser and sent only to openrouter.ai.
3. **Generation language** (optional) → top bar / Settings. Auto-ticks when
   non-English; the default is fine.
4. **Rulebook** (optional) → Rules. Auto-ticks when a book exists. Copy notes
   the loud scanned-PDF failure and that original bytes are never stored.
5. **Bestiary pack** (optional) → Settings. Manual mark only (fetched packs
   aren't cheaply detectable).
6. **First campaign + module** → picker / top-bar Module, plus the
   **First-Module Guide** in a new tab. Auto-ticks when a campaign AND a module
   exist; shows live ✓/· sub-progress.

Semantics: every step is skippable; detected completions tick automatically;
the dialog resumes at the first unresolved step; **Finish** (all resolved)
persists `complete`; **Don't show again** persists `dismissed` and never
auto-opens again. Auto-open fires once per browser and only when campaigns ==
0 (an upgraded install is never hijacked). Re-open affordances: picker header
"Get set up" + empty-card "Set up Campaigner" button, the workspace welcome
panel, and the help **setup** topic's "Reopen the setup wizard" action. All
hidden once complete (picker/welcome; help topic stays).

### Screen: First-module guide (`/guide`, `/guide/:chapterId`)

A full-page in-app route authored as structured data (`guideContent.ts`,
helpContent pattern) and opened **in another tab** (`target="_blank"`) from
the wizard's last step, the help setup topic and the modules empty state — a
same-origin tab keeps IndexedDB, so it can deep-link the reader's own
campaign. Nine chapters teach the authored path: start here → campaign →
rules & pins → create module → approve the spine → read/edit/rewrite →
resolve the cast → battlemaps → table & print. Each chapter ends with a
checkpoint line and a "Do it now" button: static routes always resolve;
campaign-scoped ones resolve against the most recently updated campaign and
render as a disabled hint while none exists. A test guarantees content
completeness and that every app link's route exists in the route table.
